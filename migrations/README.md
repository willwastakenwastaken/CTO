# Migrations

Plain SQL migrations for SignalDesk Phase 1, applied in order:

| File                       | What it does                                                                                       |
| -------------------------- | -------------------------------------------------------------------------------------------------- |
| `001_initial_schema.sql`   | Enum types, all ten tables, CHECK constraints, indexes, shared `updated_at` trigger + triggers     |
| `002_rls_policies.sql`     | Enables RLS on all ten tables, creates ownership policies, least-privilege role grants             |
| `003_ai_suggestions_superseded_by.sql` | Adds `ai_suggestions.superseded_by` (uuid FK, on delete set null) + index so superseded suggestions are marked without deleting history |

All files wrap their statements in a single `begin; ... commit;` transaction.

## How to apply

### Option A — Supabase Dashboard (SQL Editor)

1. Create a Supabase project, then open **SQL Editor** (Dashboard → SQL Editor → New query).
2. Paste the entire contents of `migrations/001_initial_schema.sql` and click **Run**.
   It must complete with no errors before continuing.
3. Paste the entire contents of `migrations/002_rls_policies.sql` and click **Run**.
4. Optionally verify: `select * from pg_tables where schemaname = 'public';` should
   show the ten tables, and `select * from pg_policies where schemaname = 'public';`
   should show the policy set described below.

### Option B — Supabase CLI

```bash
supabase link --project-ref <your-project-ref>
supabase db push   # applies migrations/ in filename order (0..9, then a-z)
```

(`supabase db push` picks up plain SQL files in `migrations/` when the project
is initialized with `supabase init`.)

## What each file does

- **001_initial_schema.sql** — creates six enum types (call status, speaker,
  event type, event category, suggestion action, prospect stage) and the ten
  tables: `profiles`, `sales_profiles`, `prospects`, `prospect_notes`,
  `activities`, `call_sessions`, `transcript_segments`, `call_events`,
  `ai_suggestions`, `product_events`. All primary keys are UUIDs generated by
  Postgres (`gen_random_uuid()`; `profiles.id` is the `auth.users.id` itself).
  CHECK constraints enforce score ranges (0–100), confidence (0–1),
  nonnegative durations/times, and suggestion feedback values. Indexes cover
  every `user_id`/FK column and the common query paths (prospects by
  user+stage, call sessions by user+status, segments by call+sequence, events
  by call, suggestions by call). A shared `set_updated_at()` trigger function
  is created and attached to every table that has an `updated_at` column.

- **002_rls_policies.sql** — enables RLS on all ten tables and defines
  per-table policies; revokes all table access from the `anon` role and grants
  full DML to `authenticated` (confined by RLS to owned rows).

## RLS model

Every user-owned table enables RLS; the browser ships only the anon key and an
authenticated user's JWT, so `auth.uid()` is always derived server-side by
Postgres — a browser-supplied `user_id` is never trusted.

- **profiles** — `id = auth.uid()` (the profile id *is* the auth user id).
- **sales_profiles, prospects, call_sessions, product_events** —
  `user_id = auth.uid()` on select/insert/update/delete.
- **call_sessions** (and others with optional parents) additionally verify on
  insert/update that any referenced `prospect_id` / `sales_profile_id`
  (`session_id` for product_events) belongs to the same user.
- **transcript_segments, call_events, ai_suggestions** — `user_id = auth.uid()`
  **and** an `EXISTS` check that the parent `call_sessions` row belongs to the
  same user. Knowing another user's call UUID can never be used to attach a
  segment, event, or suggestion to their call.
- **prospect_notes** — same pattern against `prospects` (and the optional
  `call_id` must also be owned).
- **activities** — `user_id = auth.uid()` and any present `prospect_id` /
  `call_id` must be owned.

Consequence: User A can never read or write User B's rows, and can never attach
new records to User B's parents. A two-user RLS isolation test for every table
is planned in the integration test suite (`tests/integration/`).

## Security warning — service_role

The `service_role` key bypasses RLS and grants full access to every table. It
must **never** be exposed to the browser or shipped in client code — it belongs
only in server-side environments (and ideally nowhere in Phase 1). The two
variables in `.env.example` (`NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY`) are public by design; RLS is what protects
data.

## Notes and caveats

- **Idempotency** — both files are written to be re-run safely *after a
  completed run* (types guard against `duplicate_object`, tables use
  `IF NOT EXISTS`, triggers/indexes/policies are dropped before creation).
  A run that **failed mid-way** cannot be safely resumed: `CREATE TABLE IF NOT
  EXISTS` will not repair a partially created table. If that happens, drop the
  affected tables (or use a fresh database) and re-run both files.
- **`gen_random_uuid()`** is core PostgreSQL (13+); Supabase runs 15+, so no
  extension is needed.
- **Not verified here** — these files were authored and reviewed, but not
  executed: no live database was available in the build environment. Before
  first use, confirm the applied schema with the SQL Editor queries in
  Option A step 4 and the planned two-user isolation test.
